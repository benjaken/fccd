# FCCD Customer Portal 需求規格 v1.9

版本：v1.9｜日期：2026-10-12｜語言：繁體中文｜貨幣：HKD｜時區：Asia/Hong_Kong

本版依用戶最新個人／團體流程修訂，取代 v1.8 及 CUSTOMER_ORDERING_PRD v1.4 中衝突的需求。需求來源為本次對話；實作核對基線為 develop `5278579c`。本文件是目標規格，不代表功能已完成或已部署。舊文檔保留作歷史，後續開發、驗收及配置以本版為準。

已確認：團體 BR 審核、成員各自提交後由 Admin 整批送單、FCC 確認入單後傳送工場、週／半月／月結；積分只兌換 Shopify 固定金額折扣碼及實物，不直接抵扣 Portal 訂單金額；折扣碼一次使用、不保留餘額；Portal 與對應 Shopify 客戶地址雙向同步。學校專屬模組仍不納入。

## 2 角色及頁面

FCC Admin Login 是內部員工入口，不能與團體 Admin 混用。所有操作以 user_id、有效組織／成員關係及 action 權限核實；前端隱藏不能替代 RPC／RLS 保護。

| 功能 | 個人客戶 | 團體成員 | 團體管理員 | FCC 後台 |
|---|---|---|---|---|
| 主頁 | 下一張單狀態、積分結餘、再訂一次、官網連結 | 今期截單倒數、自己申請／訂單狀態 | 已／未落單人數、倒數、本期累計金額 | 申請、收單、付款、結單、同步例外待辦 |
| 最新餐牌 | 官網連結及已授權即時訂購入口 | 公司可訂餐牌、協議價按 FCC 顯示政策 | 公司授權餐牌及價格 | 餐牌、價格、供應日及發布設定 |
| 訂購／加單 | 自己合資格訂單 | 公司地址及允許餐牌，提交待 Admin 送單 | 自己／代成員下單，整批審核送單 | 收單、確認、改單及工場交接 |
| 紀錄 | 自己訂單、明細、再訂、收據 | 只看自己申請及結果 | 全公司，按成員／日期篩選、Excel匯出 | 授權業務範圍 |
| 付款證明 | 選訂單／批次上載 | 預設無公司付款權 | 選結算單上載 | 財務核實、拒絕及付款分配 |
| 積分 | 自己結餘、流水及兌換 | 預設不能查看／使用公司分 | 公司結餘、流水及兌換 | 規則、獎賞、流水及原因式調整 |
| 地址 | 新增／編輯／刪除／預設 | 只選 Admin 授權送貨點 | 管理公司送貨點 | 同步配置、映射及衝突處理 |
| 團隊／公司 | 無團隊管理 | 顯示公司、部門、送貨點 | 新增／停用、業務權限、限額；公司資料及BR；結算週期唯讀 | BR審核、週期、公司設定及管理員核實 |

成員個人資料包含姓名、聯絡及 WhatsApp／Email 偏好；公司、部門及送貨點由 Admin 設定。個人資料包括聯絡、通知偏好及登入電郵重新驗證。所有角色有登出；切換及登出清理上下文及敏感快取。公司積分不隨成員離職轉走。

## 3 公司申請、BR 及團隊

公司申請保存公司名稱、BR號碼及有效期、BR私有附件、申請人、公司送貨點及多位聯絡人（姓名、電話、職位，可標主要聯絡人）。申請狀態：草稿 → 待審核 → 需補資料／已拒絕／已批准。FCC 核對並記原因、操作者及時間；批准後指定首位管理員及結算週期，申請人不因填寫BR自動取得公司資產。

BR到期提醒及到期後新申請／送單是否阻擋由FCC配置；既有訂單、付款及結單仍可按權限處理。續期保留歷史版本。BR不作登入憑證，也不能單憑公司名或電郵網域加入公司。

Admin新增／邀請、停用、撤銷邀請、管理員交接；最後一名管理員不能直接移除。停用即撤權，歷史歸屬保留。可設定成員可落單／只睇、餐牌子集、部門、可選送貨點及每人上限。上限支援金額／份數與按送貨日／結算期，未啟用表示無額外上限；單位及期間必填。隱價成員不得藉限額錯誤或剩餘金額查出價格。

## 4 餐牌、訂餐日曆及價格

FCC按公司、品牌、供應日期／時段、送貨點發布餐牌，設定產品、協議價、庫存／上限、最低訂量、截單及發布狀態。成員只見公司授權且符合自身子集的餐牌；Admin不能擴大公司資格。

FCC可設定成員價格顯示，隱藏時只顯示選項／數量／狀態，不顯示單價、總額、協議價或tariff；使用角色專用read model，不先傳價格再以CSS隱藏。Admin審核及FCC核價仍用伺服端真實金額。

後台月曆可按公司／品牌／送貨點查看開放日及對應餐牌；支援日曆模板、複製、個別日覆寫、節日禁單、停售及撤回發布。節日禁單優先於一般開放模板。發布前預覽公司／成員實際可見內容，檢查缺價、缺產品、無供應日及不合理截止時間。

最低訂量按送貨點及送貨日核算，支援份數／金額，是否跨同品牌餐款合計及運費規則必須配置。未達標顯示待湊單或拒絕送單；只可由有權FCC員工以原因覆核，不默默受理。

## 5 團體申請、送單及工場

成員：揀送貨日 → 揀餐及數量 → 揀公司授權地址 → 提交。提交成功顯示「已提交，等 Admin 送單」，不立即建立正式工場單、付款或積分。只睇成員前端及API均不可提交。

狀態分開保存：

- 成員申請：草稿／已提交／已撤回／被Admin退回／納入送單批次／FCC拒絕／已轉正式單。
- 送單批次：草稿／已送FCC／需確認變更／FCC拒絕／FCC已確認。
- 正式訂單：沿用履約狀態；付款、結算、退款及工場傳送各有獨立狀態。

Admin可查看、修改／刪除未送單申請，保留版本及原因，通知受影響成員；可替自己或成員提交，分開記操作者及餐點受益成員。送FCC後凍結該版本，修改走變更申請，不覆寫已送快照。再訂／範本重新驗證現價、日期、地址、權限、上限及供應。

整批送單按公司、品牌、配送日／時段及送貨點分組，不能混品牌形成一張原單。伺服端重新核對授權、限額、開放日、截單、最低訂量、價格及庫存；Admin可選本次提交範圍，一次操作可產生多個合法批次，結果逐批顯示成功／失敗，重試只處理未成功部分。

建議庫存方案：成員待審不鎖庫存；Admin送單成功原子預留，FCC確認時轉正式扣庫存，拒絕／逾期按配置釋放。預留時限及截單後待處理方案由FCC發布。改價／改量需Admin重新確認，不能靜默接受。

FCC收單隊列展示每款餐總數，以及按送貨點、部門、成員分裝明細；確認入單後連接現有orders／order_lines及工場流程。保留 request_id、批次與申請關聯，並發／重送只能成單一次、扣庫存一次、傳工場一次。

工場標籤包含送貨日／點、成員姓名或員工識別、餐款、數量及備註；FCC配置模板、排序及打印機。改單須記版本，已打印／已傳工場需變更提醒及補印版本，不能用新資料覆蓋舊標籤而無追蹤。各成員只能查自己份額，不能讀取全公司分裝清單。

Admin主頁「已落單人數」按期內有效申請的distinct成員計算；「未落單」為該期有落單資格的有效成員集合扣除已落單，不包含只睇／停用成員。需同時顯示待送FCC及已確認數量，不能將申請總額當正式收入。

## 6 個人訂購、加單及文件

個人主頁顯示下一張有效配送訂單，無單有明確空狀態；最新餐牌可連官網，即時訂購可按品牌配置 Portal 原生／官網導向。不可因導向官網就宣稱已有單一登入。

個人下單使用已授權餐牌、地址快照及伺服端價格／庫存，無積分抵扣選項；官網單須經核實customer映射才能入個人紀錄。紀錄提供狀態、明細、一鍵再訂及合資格收據；再次訂購不複製付款或賺分事件。

加單沿原品牌、配送及地址，獨立批次，只增加餐點；團體成員加單仍走Admin送FCC，不能繞過團體流程。加單截止為送貨前一天15:00，伺服端判定，等於截止拒絕；原單及付款晚回調保留既有人工受理／原路退款規則，但移除新交易的積分抵扣及其預留。團體賒帳批次按已配置結算政策處理，不強制套用個人即時付款。

原單取消、批次取消、部分退款、拒絕及改單保留稽核，不直接改已付／已送達為其他狀態。Shopify來源訂單修改依安全來源流程，不能被本地加單或地址同步覆寫。

## 7 結算單、付款核實及追數

FCC設定公司週結／半月結／月結，Admin唯讀。週結起止星期、半月分界、月結結單日、納入依據（建議已完成配送）、付款到期日及變更生效期必填並版本化；實際政策待營運發布，不擅自假定每月15日或固定信用期。

結算流程：定時產生草稿 → 對帳／核准 → 正式發布 → 未付／部分付款／已付／逾期；發布是否自動或需財務核准由FCC配置。按週期唯一鍵去重，重跑不出重複結單；以已符合納入條件的有效訂單明細形成快照，保留餐款、配送日、成員、部門、單價、數量、調整、付款分配及餘額。已納入項目不得重覆結算。

Admin查看按日期／成員／部門明細，下載PDF及訂單Excel。正式發布後不覆寫：遲到單、補差、退款及已結期間改單用調整單／下一期調整並關聯原單。Admin付款前可查看明細；結算單不等於已收款收據。

個人選訂單／批次、Admin選公司結算單，上載FPS／入數紙，保存付款日、金額、方式、參考號及附件；JPG／PNG／PDF、每次3檔、每檔10MB為既有初始方案，後台可在技術上限内配置。私有附件及限時存取，不公開BR或付款文件。

上載成功自動email通知指定FC同事，狀態為待核實；財務對款後標記已付，寫入payments及付款分配。支持部分／超額／重複／跨單分配的人工處理，總分配不能超有效入款。證明上載、付款核實、結單及訂單狀態分開，不重覆計收款。

追數提醒按到期日、頻率、收件人及模板配置；已付、爭議暫停或停用提醒不得發送；事件去重、失敗重試、紀錄可查。收據僅根據有效核實付款生成，編號、公司抬頭、條款及簽章由財務配置及確認。

## 8 積分、Shopify 折扣碼及實物

### 8.1 帳戶及規則

個人與公司使用獨立帳戶，不互轉；公司訂單不入個人分，成員不帶走公司分。已完成且已結清的合資格餐費才賺分，未結清顯示待入帳；週期付款分配至訂單後才能確認資格，重播只入帳一次。

FCC分開配置賺分率、精度、取整、有效期、合資格金額及個人Level門檻／倍率；全部版本化，不以舊版抵扣換算推定新獎賞成本。個人六級Level保留目標，可按滾動12月合資格消費升降級；舊門檻及倍率只作未發布建議，新制需營運發布完整設定。實物及券兌換本身不賺分、不計Level。

帳本記錄賺取、預留、扣除、退回、到期、追回及有原因調整。最早到期先用；退款按原有效規則追回已賺分及Level消費，不足可負分，負分不可兌換。未發布賺分規則／獎賞時不允許生效；不能任意手改餘額。

新單永不將積分作付款、抵扣餐費／運費或減少應付。歷史抵扣訂單及退款沿原支付分配處理；新舊帳本標制度版本。切換前需餘額盤點、未結預留／退款清理、遷移政策及公告，不自動重估或清空歷史分。

### 8.2 固定金額折扣碼（用戶已確認）

獎賞目錄定義所需積分、HKD固定面額、對應Shopify店舖、適用商品／系列、最低消費、有效期、可否與其他優惠合用、客戶資格、供應量及每人／每公司限額。面額與分數是獎賞配置，積分本身沒有直接抵扣價值。

兌換成功發一個專用code，於指定Shopify結帳輸入：每個已發code總使用上限一次、無剩餘面額或找續、不兌現。面額超過合資格購物金額時不留下餘額；最低消費及排除品項須在兌換前展示。不是Gift Card／store credit。本期不自動在Portal接受此code抵單。

兩種供應方式均可配置：

1. 即時建立：讀取已發布面額規則，伺服端生成不可猜測的專用code，呼叫Shopify `discountCodeBasicCreate`；確認店舖、固定金額、有效期、客戶範圍及usageLimit=1後發券。
2. 使用已有配置：FCC選Shopify既有固定金額優惠規則或已建立的未派發code庫存，API讀取並核對規則；可新增code，但不能把共用公開code當獨佔獎賞，也不能把「讀到優惠金額」當已派發。每個code需原子預留及唯一派發紀錄。

`discountRedeemCodeBulkAdd`可在既有優惠新增code，工作為非同步，須等待完成再發券。其code繼承父優惠限制，不能假設一個父優惠的usageLimit=1代表每個子code各可用一次；嚴格單次方案優先每張券建立獨立discount，或採經測試確實每code單次的既有券池。客戶限定亦須核實父優惠範圍；公司券綁定已核實公司Shopify主體或指定使用人，不能預設發給私人帳戶。

狀態：申請 → 積分預留 → 外部建立中／待核對 → 已發券 → 已使用／已過期／已撤銷。只在確認券存在且可用後扣分及展示code；未知超時先按固定request_id／預定code查詢，不能盲目新建或先退分再讓原code有效。明確失敗釋放預留；對帳worker及人工隊列處理兩邊交易不一致。

已發有效code取消退分前須確認外部撤銷且未使用；已使用不自助退分。過期、Shopify訂單取消是否返券／返分需發布政策，不自動重發。同步使用狀態需訂單事件及定期對帳，不能只靠前端點擊。code加密保存、最小存取及日誌遮罩；一般成員不能查看公司券。

### 8.3 實物

FCC配置SKU／圖片、所需分數、庫存、有效期、品牌、資格、兌換上限、取貨／配送方式、運費及履約責任人。兌換時原子預留分數及庫存，確認成功扣除並產生獨立獎賞履約單，不混作付費餐單或重複同步減庫存。

客戶查兌換及履約狀態；未履約取消由營運核准、流水退分並釋放庫存，已交付不自助退分。未到期退分沿原效期，已到期退分按已發布補償政策，建議沿用30日而非永久延長。Shopify商品同步及是否由Shopify履約是可配置模式，選擇後只有一個庫存／履約主系統。

## 9 地址雙向同步（用戶已確認）

個人地址同步至對應個人Shopify Customer；公司共享送貨點同步至核實的公司Shopify主體。公司送貨點不是每名成員私人地址，不複製BR或不必要部門資料至Shopify。若使用Shopify B2B CompanyLocation需另核對店舖方案與API，不將一般Customer地址冒充B2B權限。

建立穩定映射：owner_type／owner_id＋store_id＋shopify_customer_id；每個地址保存本地address_id、Shopify address GID、預設狀態、版本、來源、最後同步及錯誤。每店獨立映射，六品牌共用Portal帳戶不代表六個店舖自動共享Shopify地址。

Portal新增／編輯／預設／刪除排入outbox，由伺服端Admin API同步；Shopify側變更透過經簽章驗證的可用customer事件觸發重新抓取地址，另定期完整對帳補漏。個別地址事件可達性需實店測試，不能只假設每種變更均有即時webhook。Customer讀寫需取得對應scope及受保護姓名／地址／電郵／電話存取資格。

採版本化衝突處理：保存last_synced基線／摘要，只有一側改動時傳到另一側；雙方各有新版本時進人工衝突隊列，保留兩份內容及操作者，不能單憑本地時間最後寫入勝出。來源event_id／checksum去重、防同步循環；新增重試先確認外部地址映射，避免重複地址。

刪除採tombstone及外部確認，避免對帳復活地址；刪除預設地址需先選新的預設或明確保留無預設。公司Shopify地址變更屬公司地址管理，不能讓一般成員藉自己Shopify帳戶改共享送貨點。欄位轉換、香港國家／地區、電話、樓層及地址行必須往返不丟資料；不支援欄位留本地。

同步失敗顯示待同步／失敗及最後成功時間，可重試及人工處理，不顯示成功；保存地址成功與外部同步成功分開。所有已提交訂單使用地址快照，後續地址同步不改歷史或正在配送訂單。Shopify店舖離線不得丟失Portal本地地址。

## 11 通知、身份及同步共同要求

個人／團體成員的WhatsApp／Email偏好與必要帳務／安全通知分開；營銷需適用同意，必要交易通知政策由營運發布。付款證明上載、Admin送單、FCC確認／退回、工場改單、結單發布、到期／逾期、BR到期、兌換發券／履約及同步失敗各有事件、收件角色與重試設定。站內狀態不依賴Email是否送達。

Shopify API token只在Edge Functions／後台使用，固定支援版本、處理HTTP錯誤及GraphQL userErrors、限流、分頁、超時及重試；所有外部操作有outbox／idempotency／對帳，不假設跨Shopify與SQL原子交易。Webhook驗簽、事件去重及亂序防護；不把客戶電郵字串直接當身份歸屬。

官網登入即Portal登入為可行性待驗項：已查官方第三方identity provider SSO要求Shopify Plus及OIDC provider；現有Supabase OTP不等於已建立Shopify session。若不符合條件，採共用登入入口或Shopify Customer Account OAuth重新授權及穩定映射，不複製密碼、共用任意cookie或憑查單token升權。

## 15 Shopify 官方可行性依據
