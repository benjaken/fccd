# 新訂單配送與庫存規則

新訂單使用配送分配表，同一商品可分到多程。單程自動分配；多程僅在商品配送時間唯一匹配時自動分配，否則由訂單詳情的「配送分配」填寫。新增／匯入過程容許尚未建立配送，但任何一程進入待接單前，資料庫必須驗證所有商品已完整分配。這是出貨門檻，不是每次匯入明細寫入時強制非空。

進入待接單後，數量、商品、套餐選項、配送分配、取消與合併變更，會在同一交易沖銷原扣減並按最新內容重扣。沖銷流水保留，重試相同內容不新增流水。同一商品的扣減唯一鍵包含配送程次。

修改數量按原拆程比例調整，精度為 0.001；採累計四捨五入保證合計一致，零份額移除。取消一程回補該程材料，其分配保留作為已取消份額，不自動轉到其他程。整單取消或合併回補整單；合併目標按自身最新明細重新計算。

用量頁、14 日預測及逐單缺貨排序使用 `private.inventory_demand_lines`，到會用料及實際扣減共用 `private.catering_line_material_requirements`。有效 BOM 快照優先，按缺少的材料 ID 使用產品／套餐配方補足；改商品或套餐選項使舊快照失效。

餐廳訂貨保留中央倉出貨時扣庫存。未出貨需求按配送日期的香港時間 00:00 加入統一排序，同時間先預留餐廳需求，因現有資料沒有精確配送時分。

## 驗證

執行 `npm run test:inventory-sql`，在記憶體 PostgreSQL（PGlite）中載入隔離測試 schema 與實際兩份 migration；不連正式資料庫。涵蓋自動配程、4/6 拆程、重試、改量、取消、合併、套餐新增選項、部分 BOM 補包裝、同日餐廳排序與權限拒絕。

材料本身也採累計四捨五入分配到各程，預測與實際扣減使用同一結果；排序固定按配送 ID，取消或篩選日期不會把尾差轉移到其他程。用量頁按 31 日分段讀取完整選定範圍。缺少 BOM 的提示與需求共用待配送程次，因此依實際配送日期及取消狀態判斷。

配程 RPC 使用訂單 advisory lock 保護讀取及更新，不再先取得商品列 `FOR UPDATE` 鎖；等候訂單鎖後重新讀取商品數量。

Windows 可將 `embedded-postgres` 安裝在獨立暫存目錄，設定 `FCCD_PG_TEST_RUNTIME` 指向該目錄，執行 `npm run test:inventory-concurrency -- --verify-old-lock`。測試以隨機本機端口和獨立資料目錄啟動 PostgreSQL，重現舊鎖定死鎖，再驗證整單配程與單商品配程、直接改量兩種併發情境，最後關閉及清除測試資料庫。

以上測試不代表已驗證完整歷史 migration 或正式角色 JWT 權限矩陣。正式部署前仍需在 staging 套用完整 migration 並驗證實際新增／匯入流程。

## 第二輪回歸修正

空用量快照（calculated_quantity 與 ingredient_quantity 均為 NULL）不會阻擋有效配方回退。缺配方警告使用實際需求結果及訂單已選套餐商品；存在訂單選項時不再借用預設商品的配方，部分已選商品缺配方也會提示。

快照以 private.material_line_versions 與每筆 BOM 的 material_line_version 配對。商品／套餐／套餐選項改變時遞增版本，新匯入或實際改變用量／商品關聯的 BOM 記錄當前版本，舊版本不因新資料匯入而復活。套餐選項觸發器只寫入獨立版本表，避免持有訂單 advisory lock 後反向更新商品列形成死鎖。匯入應先完成商品及套餐選項，再寫入其 BOM。

新增 test/sql/inventory-bom-review.sql，涵蓋空用量回退、缺配方警告、新匯入／更新快照、舊快照隔離及實際扣減，並在 PGlite 與獨立 PostgreSQL 執行。雙連線測試增加套餐選項與商品數量競爭，--verify-old-lock 會裝回舊有反向商品列更新作對照，驗證能抓到死鎖，再恢復修正函式測試五次。

## 第三輪修正與回測

套餐選項未綁定 order_line_id 時可正常匯入、更新及刪除；稍後綁定、解除綁定或移至其他商品列時，更新受影響列的版本。重存相同選項不增加版本；BOM 的數量與商品關聯均未改變時，保留舊版本，避免 metadata 更新或重試復活失效快照。

材料快照沒有證明它涵蓋哪個套餐商品，因此包裝或其他材料的存在不能消除已選商品缺配方警告。即使可計算部分用量，也保留該警告，直至缺少的商品配方補齊。

所有訂單／配送材料聚合的直接 INSERT、UPDATE、DELETE 與 UPSERT 在 BEFORE STATEMENT 取得同一交易 advisory lock；配程 RPC 與 reconciliation 也先取得此鎖，再取得原本的訂單鎖。這使多筆交易不會在取得訂單鎖前先持有另一商品列鎖。代價是不同訂單的這類寫入也會排隊至交易結束；查詢不取得此閘門。若未來需要提高寫入吞吐量，需把全部直接寫入入口收斂到能在 DML 前取得訂單鎖的 RPC，再縮小鎖範圍。

本輪回測：PGlite SQL 回歸、獨立 PostgreSQL BOM 回歸與雙連線測試；--verify-old-lock 會停用閘門作對照，重現三種舊鎖循環，再恢復現行函式。現行套餐選項競爭與多商品交易各跑五次，另驗證批次 upsert，並檢查最終數量。相關介面與通知的四份 Vitest 測試共 24 項通過。本輪沒有部署正式環境。

## 第四輪修正與回測

切換套餐時，需求與警告只採用屬於目前套餐的選項；旧套餐選項保留作歷史資料，但不參與新套餐計算，也不阻擋新套餐預設商品。改成單一商品時同樣排除套餐選項。尚未解析商品關聯、但已屬於目前套餐的選項仍提示缺配方。

配送新增或日期／狀態變更，按整張訂單是否有已承諾配送判斷是否需 reconciliation。若改動造成配程不完整或不明確，交易會被驗證拒絕並回滾，原分配與扣減均保留；不影響分配的日期修改仍可成功。

新增 20260908224000_lock_existing_material_rpcs.sql：13 個先取得列鎖的既有 RPC 在入口取得材料寫入閘門，涵蓋批次儲存、轉單、配送、工廠、自助加購與會回算訂單的付款流程；付款與加購 checkout 的直接寫入也先取得閘門。各 RPC 原有簽名、業務邏輯、security invoker/definer 模式及既有 grants 保留，invoker 所需的鎖 helper execute 權限單獨授予 authenticated/service_role。

新增第四輪 SQL 及 RPC 權限回歸。實際 save_sales_document_batch 與直接訂單更新交錯連續五次通過；移除其入口鎖的對照函式能重現舊死鎖。原有 SQL、三組併發、批次 upsert 回歸亦通過。相關介面、通知與編輯器六份 Vitest 測試共 35 項通過。獨立 fixture 執行實際 migration/RPC，但付款總額回算等非庫存相依有 stub，並非完整正式 schema／全部 RPC 業務流程的端對端驗證。本輪未部署。
