# FCCD 餐飲訂購平台 PRD

版本：v1.5（獨立客戶路由頁面及入口）
日期：2026-10-12
語言：繁體中文；金額：HKD；業務時區：Asia/Hong_Kong

## 1. 目的與需求依據

**已確認**：FCCD 旗下有六個品牌，本平台須支援六品牌的餐飲訂購服務。代碼以 `channels` 表管理渠道／品牌；客服品牌識別及餐牌路由確認六個品牌：Food Channels Catering、Food Channels Kitchen（桂花八月）、Food Channels Express、Food Channels Cuisine（福滿樓）、HK Lunch Box、HK Party Food。logo 工具尚缺 Express 映射。實際渠道 ID 及啟用狀態仍須核對資料庫。

整合現有餐飲服務，建立企業及機構客戶的餐飲訂購入口。營運選定並授權指定餐單，客人登入後可直接選餐及落單；合資格消費累積至所屬企業／機構的積分帳戶。平台集中提供加單、付款單據、訂單紀錄及團隊管理，縮短現有落單流程。

本次已確認的核心目標：指定餐單供已登入客人使用、企業及機構層級儲分，以及提升落單速度。現有服務已確認為 React/Vite 前端及 Supabase 資料庫、RPC 與 Edge Functions；本稿按 develop 代碼校準。機構會員、指定餐單授權及積分仍屬本期新增需求，不能視為已上線功能。

本 PRD 的功能範圍以使用者提供的 sitemap 為主。HKT_午餐訂購應用程式.pdf 主要用作積分／Credit 參考，文件中的學校、學生、兄弟姊妹帳戶等情境不直接納入本產品。

需求標記：
- **已提出**：使用者明確要求的頁面及功能。
- **文件參考**：PDF 可確認的行為，不代表本產品已採納。
- **建議**：為形成可開發方案而提出的設計，需產品負責人確認。
- **待確認**：涉及營運或商業政策，不能當作既定規則。

### PDF 的積分參考

第 10 頁「訂單記錄 & 積分 / Order history & Credit」展示：
- Credit 以港幣金額顯示，例如 HK$120.00。
- Credit 明細包括 Refund 及 Expenses。
- Credit 於下一次訂餐付款時自動抵扣，餘額可用其他付款方式支付。
- 畫面有 Credit 到期提示，但未提供完整到期政策。

PDF 沒有訂明消費賺取積分比例、積分兌換率、獎勵資格或退款後獎勵追回規則。因此本 PRD 將「獎勵積分」與「退款餘額 Credit」分開；本期建立獎勵積分，退款 Credit 為可選待確認能力，不自動新增或將既有 Cashdollar 轉為積分。

## 2. 產品目標及成功指標

1. 將現有餐單、客戶資格、訂購及付款流程連接至同一入口。
2. 讓客人登入後直接取得獲授權的指定餐單及價格。
3. 以企業／機構作為儲分主體，統一累積及管理合資格訂單的積分。
4. 透過預設地址、常用訂單、再次訂購及簡化確認流程，提升首次及重複落單速度。

建議追蹤：登入至成功落單的中位數及 p90 時間、重複落單時間、再次訂購使用率、訂購完成率、需要人工跟進的比例、機構積分入帳準確率及積分使用率。以現有服務流程作基線，再設定改善目標。

## 3. 使用者及權限

| 角色 | 可執行操作 | 權限限制 |
|---|---|---|
| 客戶使用者／團隊成員 | 查看獲授權餐單、代所屬機構訂購、加單、上載單據、查看有權限的訂單及管理個人資料 | 僅存取所屬機構的獲授權資料；可使用機構積分，但不能調整儲分比例或餘額 |
| 企業／機構管理員 | 管理成員及地址、查看機構訂單與積分、建立集中訂單、按政策兌換積分 | 僅限所管理機構；不能修改營運授予的餐單或 tariff 資格 |
| 營運人員（支援後台） | 管理餐牌、價格、庫存、截單時間、配送、訂單及退款 | 按後台角色授權 |
| 財務人員（支援後台） | 審核單據、核實付款、記錄退款及帳務調整 | 不因財務角色自動取得所有管理權限 |

企業／機構為客戶及積分歸屬主體，「團隊管理」為其管理成員的入口。MVP 每個使用者只屬於一個有效機構；成員可按權限代表機構下單，訂單同時記錄機構及下單人。付款責任按現有服務政策設定。獨立個人客戶及個人儲分不列入本次核心範圍。

## 5. 功能需求

### F01 主頁

**已提出**：主頁及各功能入口。

建議展示：使用者名稱、所屬企業／機構、獲授權的指定餐單、下一張待配送訂單及待付款提示。有權限者可查看機構積分。主要按鈕為「立即訂購」，並提供「再次訂購」、常用訂單及可加單訂單入口。

驗收：未有訂單時提供訂購入口；有待處理付款時提示連結至正確訂單；餘額及訂單摘要與詳情頁一致。

### F02 最新餐牌及指定餐單

**已確認方向**：Normal / ABC 為同一指定餐單的兩套價格。機構適用哪套價格由 FCCD 授權，實際價目表仍需提供。

**已提出**：由營運選定指定餐單，客人登入後使用。餐單授權與 tariff 資格分開管理：先判斷客戶可使用哪些餐單，再套用其 Normal／ABC 價格。建議預設按企業／機構授權，若現有服務有個別客戶例外，另行確認。

未登入不能進入訂購流程；登入後只顯示獲授權且有效的餐單。每款餐點包括名稱、照片（可選）、描述、價格、供應日期、可訂數量、售罄狀態及餐牌版本。過敏原資料如有提供須清楚呈現。

價格及餐牌按生效日期管理；購物車顯示實際單價、數量、優惠及總額。客戶端所有頁面及單據均隱藏 Normal／ABC／tariff、價格類別、已套用某價格提示及價格方案切換；兩套價格只在 FCCD 後台管理及服務端核價。訂單保存提交時的價格快照。

驗收：未獲授權餐單不可透過網址或請求查看及訂購；沒有 ABC 資格的帳戶不能取得 ABC 結算價；授權失效後不能新下單但保留合法歷史紀錄；售罄不能提交；價格或庫存改變須重新確認。

### F03 即時訂購

流程：登入並取得所屬機構與指定餐單 → 選擇餐點、數量及配送日期 → 在同一確認頁檢查預設地址、時段、金額及抵扣 → 提交訂單 → 付款指示。已有有效資料時不要求重新輸入機構、聯絡人及地址。

快捷落單需求：
- 自動帶入機構、適用實際價格、預設地址、聯絡資料及有效配送時段，使用者可在權限內修改。
- 「再次訂購」複製歷史訂單餐點及數量至購物車，以現時價格、餐單授權、庫存及配送條件重新驗證；不直接複製付款或積分交易。
- 「常用訂單」可保存常用餐點及數量；失效餐點提示替換，仍可繼續修改其餘項目。
- 支援同頁調整數量、自動計算金額及保存未提交購物車；提交前仍需明確確認。
- 建議一般落單在選餐後只需一次確認頁；再次訂購以「再次訂購 → 檢查／調整 → 確認」完成。登入及外部付款不計入此操作目標。

必填：訂單擁有人、配送日期／時段、餐點、數量、送貨地址、收件人及電話。支援訂單備註；是否接受餐點客製化待確認。

伺服器須驗證資格、截單時間、配送區、庫存及金額；提交時重新檢查，不只依賴前端。使用者重按提交或網絡重試只能建立一張訂單。未成功時保留購物車並顯示可處理原因。

驗收：成功後取得唯一訂單編號及應付金額；重試不重複扣庫存或積分；截單後拒絕提交並顯示下一個可訂日期。

### F04 加單

**代碼現況**：自助加單使用 PayPal；付款完成後將餐點加入原單的 `order_lines`，標記 `is_addon=true` 及 `addon_checkout_id`，付款記錄亦關聯原單。原單總額會重新計算，並非另建加單訂單。截止為送貨前一天香港時間 15:00，另有禁加單日期及可加單商品設定。

**已確認的實作方案**：沿用同一原單的加單批次，原有餐點及付款交易不覆寫；保留加單批次編號、餐點、當時價格、付款及退款流水。帳面總額因有效加單增減重新計算，原單號保持不變，不要求另建訂單號。原單與有效加單一起備餐及配送。

**已確認的目標規則**：
- 加單截止為送貨前一天香港時間 15:00，15:00 起拒絕新提交；截止前建立購物車但截止後提交亦拒絕。
- 使用加單當時適用價格。現有實作用 `price_override` 優先、否則 `products.price`；本期須加入機構價格資格並保存價格快照，客戶端不展示價格類別。
- PayPal 保留為現有付款能力，成功支付後自動建立付款紀錄，不要求重交付款單據。本期新增手動付款及單據流程：截止前完成付款並提交單據，未完成則不接受加單，原單照常處理。及時提交但尚待財務審核不可僅因審核延遲自動拒絕。
- 本期新增積分抵扣；加單應付零時免付款及單據，仍須截止前提交。抵扣及付款必須使用同一服務端結算結果。
- 原單取消成功，所有有效加單批次一併取消；只取消某加單批次，原單及其他有效批次保留。
- 加單沿用原單配送資料；不同日期、時段或地址須另建原單。
- 現有後續 migration 已開放跨渠道加單商品，不可誤寫為已具備機構指定餐單授權。本期授權範圍須獨立建立；本期原單只屬一個品牌，加單商品亦須屬原單品牌；現有跨渠道加單 RPC 須在服務端收窄，不能只在前端過濾。

驗收：同一付款重試不重複加行或付款；取消加單只撤銷該批次明細並重算總額；原單取消停止整單配送；批次結算／審核不影響原單既有付款交易。原有 Shopify 明細不得因本平台加單修改被覆寫。

### F05 上傳付款單據、審核及下載

**已確認**：積分全額抵扣餐費後，如仍有運費或其他應付金額，須支付剩餘款項；如整張訂單應付金額為零，直接顯示「已結清（積分抵扣）」，毋須上載付款單據。加單應付為零時，毋須付款及提交單據，但仍須於截止時間前提交訂單。

選擇有權限的機構待付款訂單，展示應付餘額及收款資料，輸入付款日期、付款金額、付款方式及參考編號（如有），上載並預覽單據後提交。

建議支援 JPG、PNG、PDF；單檔上限 10MB，每次最多 3 個，數值可配置。伺服器驗證實際檔案格式、大小及惡意內容。單據須私有儲存及受權限保護。

狀態為「未提交 → 待審核 → 已核實／需重新提交」。上載成功僅代表收到單據，不能直接標為已付款。審核拒絕需提供原因，重交保留版本歷史。金額不足、過多或疑似重複由財務處理，不自動假設足額。

建議 MVP 每次單據提交僅關聯一張訂單；團隊集中訂單可包含多份餐。跨多張訂單合併付款另作需求。

驗收：上載失敗可重試；上載成功顯示待審核；未授權帳戶無法下載；同一付款不得被重複核實入帳。

### F06 訂單紀錄

提供列表、配送日期／狀態／下單人與團隊篩選及訂單編號搜尋。詳情顯示餐點、價格快照、配送地址快照、加單、應付及已付金額、抵扣、付款單據狀態、配送進度及取消／退款進度。

分開呈現三種狀態：
- 履約：已確認、準備中、配送中、已完成、已取消。
- 付款：待付款、待審核、部分付款、已付款。
- 退款：無退款、待處理、部分退款、已退款。

取消資格由截止時間與履約進度決定。建議 MVP 透過「申請取消」由營運處理；取消是否成功及退款金額須明確通知。取消成功不等於退款完成。

驗收：付款待審核不覆蓋配送狀態；地址簿修改不改變舊訂單；成員無法查閱未獲授權的其他成員訂單。

#### F06.1 按訂單來源限制狀態修改

**已確認**：Shopify 修改須由 FCCD 按截單時間及履約進度核對是否接受。收到外部修改而尚未完成核對時，展示「修改待確認」，保留 FCCD 原有正式狀態；核對接受後更新正式紀錄，未接受則提供原因及營運跟進入口。Shopify 修改截止為送貨前一天香港時間 15:00，15:00 起的修改交由營運個別處理，不自動承諾接受；具體可接受的狀態轉換仍待配置。

**已提出**：只有加單及手動新增的訂單支持用戶在本平台更改狀態。由 Shopify 匯入的訂單，需前往 Shopify 自助修改。此限制優先於其他章節的一般狀態操作描述。

| 訂單來源／類型 | 本平台用戶修改狀態 | 操作方式 |
|---|---|---|
| 本平台新增的加單 | 支持，須符合角色權限及允許的狀態轉換 | 提供「更改狀態」 |
| 手動新增訂單 | 支持，須符合角色權限及允許的狀態轉換 | 提供「更改狀態」 |
| Shopify 匯入訂單 | 不支持 | 顯示「此訂單來自 Shopify，請前往 Shopify 修改」及自助修改入口 |
| 其他來源／來源未明訂單 | 不開放，待確認 | 唯讀展示，先核實來源 |

功能及權限要求：
- 列表及詳情顯示來源標籤；來源由系統保存，用戶不能自行改為手動訂單以取得修改權限。
- 來源資格與角色權限須同時符合，不能因屬於加單／手動訂單而取得所有狀態操作權。
- 前端僅為符合資格的訂單提供修改操作；伺服器對單筆、批次及直接 API 請求執行相同限制。批次包含 Shopify 訂單時須列出不可修改項目，不更新其狀態。
- Shopify 訂單的取消或其他會更改狀態的用戶操作亦須轉往 Shopify；查看訂單及上載單據不等同獲准更改其 Shopify 狀態。
- Shopify 原單的本平台新增加單須在原單內保存加單批次來源；只可修改符合資格的加單批次，不得改寫 Shopify 原單明細或正式狀態。加單若本身亦由 Shopify 匯入，仍按 Shopify 來源限制。
- FCCD 為訂單狀態的最終依據。客戶在 Shopify 修改後，變更須同步至 FCCD，由 FCCD 核對及記錄，再更新本平台展示；展示最後同步時間。同步延遲／失敗須有提示，不先顯示未確認的新狀態。來源衝突須留待營運處理，不以 Shopify 資料直接覆蓋 FCCD 已確認紀錄。
- 記錄操作者、時間、原狀態、新狀態及原因。其他頁面的操作入口及提示須遵守同一來源限制。

**已確認**：客戶可申請取消符合資格的加單／手動訂單；已付款、已配送及已退款等確認狀態由財務、營運或系統按職責更新，客戶不能自行標記。Shopify 訂單向客戶提供前往 Shopify 修改的指引，不在 FCCD 開放客戶直接修改。待確認具體允許的狀態轉換、取消截止時間，以及 Shopify 指引內容及入口。

驗收：有權限用戶可修改加單及手動訂單的允許狀態；Shopify 訂單在介面、API 及批次操作均不能由用戶在本平台改狀態；Shopify 修改結果同步後才更新顯示；操作加單不改動 Shopify 原單。

### F07 獎勵積分及 Credit

**已提出**：以企業及機構為儲分主體。機構內不同獲授權使用者下單，合資格消費均累積至同一機構積分帳戶，保留下單人及來源訂單以供追溯。成員離職或被移除不帶走機構積分。**已確認**：所屬機構的有效登入用戶均可使用該機構積分，毋須額外由管理員授予兌換資格。使用時須展示共用餘額及本次扣分，記錄操作用戶及關聯訂單；完整明細的查看範圍另按資料權限設定。

**文件參考**：以港幣顯示的 Credit、自動抵扣、退款／扣款明細及到期提示；此為獨立可選能力，不能代替本次企業／機構儲分需求。

建議頁面分兩區，單位不可混用：

| 類型 | 單位 | 來源 | 用途 |
|---|---|---|---|
| 企業／機構獎勵積分 | 分 | 該機構符合資格的完成訂單或活動 | 由所屬機構有效登入用戶使用，100 分抵扣 HK$0.1 |
| 退款餘額 Credit（如啟用） | HKD | 經核准轉入帳戶的退款／帳務調整 | 下次訂單抵扣 |

積分展示可用、待入帳、已預留及即將到期數量；明細展示交易時間、種類、增減、有效期及關聯訂單。Credit 另顯示港幣餘額及明細。

#### F07.1 儲分比例配置

**已確認的兌換規則**：100 分抵扣 HK$0.1。抵扣金額（HKD）＝使用積分 ÷ 1,000；賺取比例與兌換率為兩個獨立規則，本期僅已要求賺取比例可配置。

例：合資格餐費 HK$100，按暫定賺取比例獲 10,000 分；該 10,000 分於可用後可抵扣下一張訂單餐費 HK$10。結算頁顯示使用分數、抵扣金額、剩餘應付及使用後積分餘額。扣分及金額計算須在 FCCD 驗證，抵扣不得超過可用積分或可抵扣訂單金額，不產生負應付金額。已確認積分可抵扣餐費，運費不列為可抵扣範圍；可全額抵扣餐費，運費另付；每次以 10 分為單位，即抵 HK$0.01。使用分數須為 10 的整數倍，少於 10 分的餘額保留，不能自動向上湊整抵扣。

**已確認**：機構共用積分須支援並發使用而不超額扣分；每次使用記錄操作用戶、分數及關聯訂單。成員離職、停用或被移除後，即時失去機構積分使用權。提交兌換時重新驗證成員資格及共用餘額。

**已提出**：每 HK$1 對應多少獎勵積分可配置，積分累積至訂單所屬企業／機構。

後台提供「每 HK$1 可獲積分」欄位，設定值為 R。基本計算為「合資格消費金額（HKD）× R」，向下取整至整數分。賺取比例與積分兌換價值分開設定。

建議配置要求：
- 僅獲授權的營運管理員可設定；記錄修改人、時間、舊值、新值及生效時間。
- R 須為有效非負數；建議 0 表示暫停賺取積分，不影響既有餘額及使用。小數精度及最大值待確認；計算採精確十進位數值。
- 每次變更建立規則版本；建議按訂單建立時間套用已生效版本，提交時保存比例、合資格金額及規則版本。實際入帳於訂單完成後觸發。
- 新比例不追溯改寫已有訂單或已入帳積分；歷史調整須另作有原因的調整流水。
- 加單批次及手動新增訂單按自身建立時間套用規則；Shopify 匯入訂單以來源訂單建立時間匹配有效版本，同步重試不改用新比例或重複儲分。啟用前的歷史訂單不補發積分；找不到有效版本時不擅自套用目前比例，列為待處理。
- 建議 MVP 採全平台統一比例；是否需要個別企業／機構比例另行確認。

**已確認的暫定初始值**：每 HK$1 合資格餐費賺取 100 分（R=100），後台仍可調整。例如合資格餐費 HK$100 可獲 10,000 分。此值是賺取比例，並非積分兌換率；**已確認兌換率：100 分抵扣 HK$0.1**。每筆完成訂單的計分餐費乘以該筆規則比例後，向下取整至整數分。加單批次保存自己的比例及計分餐費，入帳按批次來源去重；不得因拆分餐點行而多次取整。

驗收：生效時間之後建立的合資格訂單使用新比例，之前的訂單沿用原版本；未授權角色不能修改；無效數值被拒絕；同一訂單重試不重複加分。若允許 R=0，對應訂單不賺分且不清除既有餘額。

建議規則：
1. 獎勵積分於訂單完成後入帳；採用訂單建立時保存的規則版本。
2. **已確認**：以餐費儲分，運費不儲分。按優惠及積分抵扣後的餐費計算，運費不計。例如餐費 HK$100，積分抵 HK$10，計分餐費為 HK$90，可賺 9,000 分。Credit 支付餐費是否儲分仍待確認。
3. 結算先顯示可抵扣額及現金餘額；如採用 PDF 自動抵扣模式，確認頁須展示 Credit 的實際抵扣金額。
4. 訂單提交時預留抵扣資產；確認後扣除；提交失敗或取消成功時按政策釋放／退回。預留期間不能在另一訂單重複使用。
5. 退款時分別處理現金、Credit 及已使用積分；已賺取積分依退款比例及取整政策追回。
6. 所有入帳、扣減、退款、到期及人工調整形成不可覆寫的交易流水，以沖銷紀錄修正。
7. 到期檢查須考慮已預留交易，避免結算中資產被重複扣減；退款退回的積分如未到期，沿用原到期日；如已到期，給予自退回入帳起 30 日使用期。

**已確認**：訂單完成後積分入帳，有效期暫定一年。每筆入帳形成獨立到期批次，先使用最早到期批次；入帳滿一年當日香港時間 23:59:59 到期，2 月 29 日入帳則翌年 2 月 28 日 23:59:59 到期。退款追回已賺積分時若餘額不足，允許機構帳戶出現負分；負分不能用作抵扣，後續賺分先填補負分。正常兌換仍不得超額扣分。

待確認：儲分比例配置的精度及上限、既有 Cashdollar 支付餐費的儲分處理、其他優惠疊加，以及是否另啟用退款 Credit。積分歸屬已確定為企業／機構。本期採積分抵扣餐費；其他獎勵兌換形式不列入本期範圍。

計算示意（不是已確認商業規則）：餐費 HK$100，可用 Credit HK$20，使用積分折抵 HK$10，則其餘應付 HK$70；該筆可賺積分仍需依核准規則計算。

驗收：頁面明確分開「分」與「HKD」；兩張訂單同時使用餘額不會超額；付款重複通知不會重複入分；部分退款可追溯至原交易；過期項目不能新作抵扣。

### F08 團隊管理

展示團隊名稱、管理員、成員及邀請狀態；管理員可發送邀請連結、取消邀請、移除成員、修改團隊資料及指定共享地址。邀請須有有效期限，接受時驗證帳戶及團隊資格。

集中訂單可記錄每份餐的成員歸屬，訂單歸屬企業／機構，並記錄下單管理員及按現有政策指定的付款人。團隊 tariff 由營運設定，不能自行提高優惠資格。

驗收：普通成員不能管理角色；最後一位管理員離開前必須交接；成員被移除後不能取得團隊資料，但歷史訂單及帳務保留；機構積分不因成員離開而轉移或清除。

### F09 送貨地址

建立、修改、刪除及設定預設地址；欄位包括地址標籤、收件人、電話、地區、街道／大廈、樓層／室號及配送備註。個人地址與團隊共享地址分開授權。

選取地址時驗證配送區及可用時段。已下單的地址保存快照；更改已確認訂單地址需經營運流程及配送可行性檢查。

驗收：不能提交缺少必填欄位或不支援配送的地址；刪除地址簿項目不影響舊單；只有團隊管理員可編輯共享地址。

### F10 個人資料及登入支援

個人資料包含名稱、電話、電郵及密碼設定；團隊資料為受控資料，客戶端不顯示 tariff。現有自助入口以電話及電郵匹配訂單，並非機構會員登入；本期需新增機構成員身份及可撤銷的會員 session。已確認採電郵及密碼，由機構管理員邀請成員，提供電郵驗證及忘記密碼流程。現有電話＋電郵入口保留作合法查單，不提供機構積分或成員管理權限。

修改登入電郵／電話須重新驗證；敏感資料變更需核實身份；密碼重設連結須限時及單次使用。

驗收：資料儲存後各頁一致；未驗證的新登入資料不直接替換舊資料；個人資料頁不能自行改 tariff 或角色。

### F11 登出

撤銷目前登入 session 並返回登入頁；伺服器拒絕使用已撤銷 session。共用裝置不應在登出後透過返回鍵取得有效的訂單或單據內容。

驗收：登出後再次存取受保護頁面需登入；重新登入可取得已儲存訂單，購物車保存策略另行確認。

## 6. 核心跨頁流程

### 客戶快捷訂購及付款
登入 → 指定餐單／再次訂購 → 日期、餐點及數量 → 確認預設地址與金額 → 提交 → 付款及上載單據 → 核實 → 配送完成 → 合資格積分入帳至企業／機構。

### 團隊訂購
管理員建立團隊及共享地址 → 邀請成員 → 建立集中訂單並記錄餐點歸屬 → 提交及付款 → 查閱團隊配送狀態。成員自行選餐的共同購物車不列入 MVP。

### 加單
訂單紀錄 → 選擇可加單原單 → 新增餐點 → 核實原配送資料及額外金額 → 提交關聯加單 → 補付及提交單據。

### 取消及退款

**已確認**：只取消加單時原單保持不變，營運從同一備餐及配送組別扣除已取消加單的餐點；只處理該加單批次的退款及積分調整。原單取消則一併取消所有有效加單。

**已確認的退款原則**：現金支付部分按原付款方式退款，積分抵扣部分退回積分；已賺取積分按退款所對應的餐費比例追回。若已賺積分已花掉而餘額不足，可產生負分。部分退款按原訂單保存的支付分配及儲分版本處理，不以目前比例重算；退回積分未到期沿用原到期日，已到期給予 30 日使用期；Credit 支付部分的退款方式另行確認。

**已確認**：原單取消成功後一併取消所有有效關聯加單。FCCD 須整組更新配送清單，停止相關備餐／配送任務；已備餐或已配送時，依取消資格核對，不保證可取消。按原單及各加單批次的支付分配計算退款、抵扣退回及已賺積分調整，分別保留交易關聯，避免漏退或重複退款。履約取消成功不等於退款完成；涉及 Shopify 的外部同步失敗須標示並交由營運跟進。
申請取消 → 營運審核 → 更新履約狀態 → 計算退款及抵扣退回 → 財務執行 → 調整積分流水 → 通知結果。退款來源、方式、時間及 Credit 轉入資格須以確認政策為準。

## 7. 現有服務整合及必要支援後台

**已確認**：FCCD 為餐單、價格資格、訂單、付款及積分的最終業務依據。Shopify 為外部訂單來源及該來源訂單的客戶自助修改入口。外部變更須同步、核對及記錄至 FCCD 後才作為平台的正式結果；同步事件保存來源識別碼及處理紀錄，重試不重複建單、入帳或儲分。衝突與失敗交由營運處理，不能以最後收到的外部資料無條件覆蓋 FCCD。

## 12. 整體驗收場景

1. 合資格使用者按正確 tariff 下單，截單、售罄及配送區限制有效。
2. 提交按鈕重按與網絡重試不造成重複訂單、扣庫存或扣抵扣資產。
3. 已付款原單成功加單，原有交易保留，加單批次及付款可追溯，整單總額依有效明細重新計算。
4. 上載單據後顯示待審核；財務拒絕可重交，核實後金額及付款狀態正確。
5. 未授權使用者不能查看其他客戶／機構的訂單、單據及帳務資料。
6. 積分與 Credit 單位分明；並發抵扣、重複付款通知、到期、取消及部分退款不重複入帳或扣帳。
7. 修改地址或餐牌價格後，歷史訂單仍顯示原有快照。
8. 取消訂單時，履約、付款及退款狀態分別正確更新，關聯加單有明確處理結果。
9. 管理員交接、移除成員及登出後，權限即時符合新狀態。
10. 登入後僅可使用獲授權指定餐單；不同機構的餐單及價格資格互不洩漏。
11. 同一機構的不同成員合資格訂單累積至同一機構帳戶；離職不轉走積分，所屬機構有效登入用戶均可使用積分，其他機構用戶不能使用。
12. 再次訂購帶入有效資料並重新核價；餐點失效或售罄有明確提示，不要求重填已有效的機構及地址資料。
13. 現有訂單渠道同步失敗可追蹤及重試，重試不重複建單或儲分；匯入資料可與來源核對。

本稿可用於產品、設計、開發及營運討論；P0 決策確認後，再凍結商業規則並拆分開發工作。

### 15.3 資料及接口沿用方案

- 沿用 `orders`、`order_lines`、`payments`、`channels`、`products`／`packages`、`deliveries` 及既有快照欄位，不另建平行營運訂單系統。

- 新增機構、成員、餐單授權、機構價格、常用訂單、付款證明及積分所需資料。先核對現有 `customers` 與機構的對應，不能憑公司名稱或共用電話電郵自動合併。
- 加單保留 `addon_checkout_id` 交易關聯；擴充手動付款及積分時，建立可取消／可退款的批次生命週期，不要求獨立訂單號。拒絕單據或未完成付款的批次不可進入正式備餐明細。

## 16. 付款及文件流程（最新確認）

客戶上傳付款單據 → 財務審核 → 核實付款入帳 → 客戶下載收據及發票。上傳成功不等於付款成功。未審核、被拒絕或尚未結清時不開放已核實收據／發票；拒絕顯示原因並可重新上傳，保留歷史版本。已核實線上付款直接使用系統付款紀錄，毋須再上傳單據。積分全額結清且無其他應付金額時免付款單據，可下載結清文件。收據及發票由 FCCD 訂單、有效付款及價格快照生成，客戶不能自行修改金額；服務端驗證機構權限及付款資格後才提供內容。

## 17. 多頁路由及 /customer 入口（已確認）

客戶功能使用獨立路由及頁面元件，不能只用本地 tab 狀態切換同一頁。共用登入、機構資料及導航外框，各路由支援直接連結、重新整理及瀏覽器前進／返回。

| 路由 | 頁面 |
|---|---|
| `/customer` | 客戶入口：未登入顯示會員登入，登入並通過機構資格後為主頁 |
| `/customer/menus` | 獲授權餐單列表 |
| `/customer/menus/:menuId` | 指定餐單、選餐及結算 |
| `/customer/orders` | 訂單紀錄列表 |
| `/customer/orders/:orderId` | 訂單詳情、再次訂購及取消申請 |
| `/customer/receipts` | 上傳付款單據、審核結果、下載收據及發票 |
| `/customer/points` | 機構積分餘額及流水 |
| `/customer/team` | 團隊管理，僅機構管理員 |
| `/customer/addresses` | 送貨地址 |
| `/customer/profile` | 個人資料 |

現有「客戶工作區」入口改指向 `/customer`。既有 `/self_service_search` 及其訂單路由保留為電話＋電郵查單，登入頁提供相應連結。查單不等於會員登入，不取得機構積分或團隊管理權限。

未登入直接進入子頁須先登入，登入後保留所要求的合法頁面。未獲授權的餐單／訂單識別碼返回相應列表；非管理員進入團隊管理返回客戶主頁；未知路由返回 `/customer`。部署使用現有 SPA rewrite，直接載入子頁不應出現 hosting 404。

個人訂單意見頁：獨立路由固定提供返回訂單紀錄的連結；無可填寫資料時顯示空狀態說明，載入失敗提供重試，頁首顯示訂單意見。機構訂單詳情內嵌意見維持原有顯示規則。
