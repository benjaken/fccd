# WhatsApp 非辦公時間自動回覆配對方案

## 1. 建議結論

自動回覆應由目前偏寬鬆的「全文模糊搜尋 FAQ」改為兩層路由：

1. 先判斷客人的業務意圖：查現有訂單、即日訂餐、非即日訂餐、一般資料、改單／投訴，或純打招呼。
2. 只有「一般資料」才進入 FAQ 關鍵字配對，而且必須符合本文件的必要詞組、排除詞及優先級，才可直接回覆。

建議開場：

> 你好，請問是查詢現有訂單，還是需要到會訂餐協助？

系統不應因電話號碼未配對客戶資料而主動提示「查無此號碼」或「未登記此電話號碼」。只有客人明確查詢現有訂單時，系統才查訂單；查不到時也只說暫時未能定位訂單，不評論電話是否已登記。

## 2. 服務時段

| 日子 | 自動回覆時段（香港時間） | 設定值 |
|---|---|---|
| 星期一至五 | 19:00 至翌日 09:00 | `19:00` → `09:00` |
| 星期六 | 全日 | `00:00` → `00:00` |
| 星期日 | 全日 | `00:00` → `00:00` |
| 時區 | 香港 | `Asia/Hong_Kong` |

系統現有排程已把「開始時間等於結束時間」解讀為全日，因此星期六、日可直接使用 `00:00` → `00:00`。平日建議先固定至上午 09:00，與目前客服回覆文案及既有設定一致；如最終決定上午 08:00 開始人工服務，只需調整平日結束時間。

### 建議固定文案

| 情況 | 建議回覆 |
|---|---|
| 純打招呼／意圖不清 | 你好，請問是查詢現有訂單，還是需要到會訂餐協助？ |
| 明確表示未訂餐 | 明白。請問你是需要即日訂餐協助，還是預先安排其他日子的到會？ |
| 明確查單但找不到 | 我暫時未能定位相關訂單。你可以傳送訂單號碼；如果是即日訂餐需要，我可以即時轉交同事協助。 |
| 即日訂餐 | 你好，已收到你的即日訂餐需要，我已即時轉交同事跟進。未收到同事確認前，系統未能保證當日供應；你可以繼續提供人數、時間、地址及想訂的品牌。 |
| 一般 FAQ 未能確定 | 我想確認一下，你是想查現有訂單，還是查詢餐牌、運費或付款等一般資料？ |

## 4. 第二層：FAQ 關鍵字對照表

### 配對規則

- `必要詞組`：每個括號代表一組；每組至少命中一個詞。例如「品牌詞」＋「餐牌詞」兩組都要命中。
- `可直接命中的完整短語`：命中後可直接對應，不必再依賴模糊搜尋。
- `排除／改路由`：命中時不可回覆該 FAQ，應按指定意圖處理。
- 同一句命中多個 FAQ 時，只在第一名分數足夠高而且明顯高於第二名時直接回答；否則先澄清。
- 泛詞如「付款」「送貨」「餐牌」「地址」「網站」「訂餐」不可單獨決定 FAQ。

## 5. 不應由 FAQ 自動作答的關鍵字

| 關鍵字／情況 | 動作 | 原因 |
|---|---|---|
| 即日、今日、急單、三／四小時後，並同時有明確訂餐需要 | 即時轉人工 | 時效高，不能被 Express FAQ 吞掉 |
| 改期、改地址、改時間、取消、退款、加單、付款未入帳 | 訂單人工跟進 | 會改變客戶個案或涉及付款 |
| 投訴、送遲、送錯、送漏、食物質素 | 人工跟進；可先提示保留訂單號及相片 | FAQ 不可承諾賠償或退款 |
| 指定菜式更換、配料更換、季節產品、特別送貨時間 | 廚房／營運確認 | 供應及安排會變動 |
| 銀行戶口、PayMe、八達通 token、月結、支票 | 人工確認 | 敏感或可能變動的付款資料 |
| 最低消費、截單時間、特別價格、加熱爐價格 | 只可引用已核准且按品牌發布的資料；否則人工 | 不同品牌及時間可能不同 |
| 純問候 | 開場澄清 | 不查電話、不回「未登記」 |

## 6. 建議配對資料結構

現有 `keywords` 是逗號字串，只能表示「命中任一詞」，無法表達必要詞組、排除詞或路由優先級。建議增加獨立規則表，而不是繼續把所有邏輯塞入 `keywords`：

| 欄位 | 用途 |
|---|---|
| `faq_id` | 對應現有已發布 FAQ |
| `intent_key` | 例如 `search_faq`、`browse_menu` |
| `exact_phrases` | 可直接命中的完整短語及同義句 |
| `required_groups` | JSON 陣列；每一組至少命中一個詞 |
| `excluded_terms` | 命中即禁止使用此 FAQ，改走其他意圖 |
| `priority` | 同時命中時決定業務優先次序 |
| `min_score` | 此條規則可直接回覆的最低分數 |
| `enabled` | 可獨立停用錯誤規則 |
| `notes` | 給客服同事理解規則，不送給客人 |

範例：

```json
{
  "faq_question": "運費幾多？",
  "exact_phrases": ["運費幾多", "送貨費點計", "delivery fee"],
  "required_groups": [
    ["運費", "送貨費", "delivery fee", "免運"]
  ],
  "excluded_terms": ["幾時送到", "送貨狀態", "我的訂單", "我張單"],
  "priority": 80,
  "min_score": 80
}
```

## 7. 建議計分及決策方式

| 證據 | 分數 |
|---|---:|
| 完整句或核准別名完全命中 | +100 |
| 每個必要詞組成功命中 | 每組 +35 |
| 高辨識度專有詞（品牌名、菜式名） | +40 |
| 一般輔助詞 | 每個 +10，最多 +20 |
| 只靠 trigram／模糊相似度 | 最多 +20，只可用來排序，不可單獨直接回答 |
| 命中排除詞 | 直接淘汰該 FAQ |

直接回覆條件建議同時滿足：

1. 第一名至少 80 分；以及
2. 第一名比第二名至少高 20 分；以及
3. 沒有任何更高優先級的業務意圖。

未達條件時，系統只問一條澄清問題。例如只收到「付款」，應問「請問你想查付款方式、貨到付款，還是已付款但遇到問題？」而不是任意選一條付款 FAQ。

模型如保留，只可在已通過規則的候選 FAQ 中做重排或把核准答案縮短；沒有 FAQ 來源時不得自行生成政策、價錢或營運答案。

## 8. 目前邏輯需要調整的重點

1. 現有資料庫搜尋在任何一個關鍵字命中時即加很高分；例如「送到」「網站」「地址」等泛詞可能令不相關 FAQ 排到前面。
2. 現有強命中判斷把「付款」「餐牌」「飯盒」「自取」等泛詞視為足夠證據，無法分辨同一主題下的不同問題。
3. FAQ 預先搜尋發生在最後業務路由之前，應改為先完成即日、改單、投訴、查單等路由，再容許一般資料進 FAQ。
4. 現有無 FAQ 來源的模型後備答案可能令回覆看似流暢但缺乏核准依據；非辦公時間應改為澄清或轉人工。
5. 現有查不到訂單文案直接提及 WhatsApp 號碼，應改用本方案的中性文案。
6. 現有純問候會回一般功能介紹；應改成清楚的二選一意圖問題：「你好，請問是查詢現有訂單，還是需要到會訂餐協助？」

## 10. 推行次序

1. 先更新問候、查不到訂單及 FAQ 不確定時的固定文案。
2. 把即日、改單、投訴、付款爭議、查單路由移到 FAQ 之前。
3. 建立結構化 FAQ 配對規則，先錄入本文件的高流量條目。
4. 將星期六、日設為 `00:00` → `00:00`，平日保持 `19:00` → `09:00`。
5. 關閉「沒有 FAQ 來源時自由生成答案」；低分或分數接近時改問澄清問題。
6. 以本文件驗收案例建立自動測試，再用過往錯配訊息做回放測試。
7. 先在測試號碼／develop 通道觀察至少一週，記錄命中 FAQ、分數、排除原因、是否澄清及是否轉人工。
8. 每週只根據已人工確認的錯配更新別名或排除詞；FAQ 內容審批與配對規則審批分開。

此方案只調整客服入站回覆的配對與非辦公時間行為，不改動既有訂單通知模板、通知自動／手動政策、參數映射、啟用或部署狀態。

## 11. 舊分支復查：`origin/cursor/same-day-urgent-develop-staff-fdf9`

結論：不要直接合併此舊分支。它想解決「即日到會客人補充資料時，沿用原有緊急跟進」的方向合理，但對話狀態不足以安全判斷緊急程度，會產生以下問題：

1. `awaiting_human` 且沒有 `selected_order_id` 被一律推斷為 `catering_inquiry`。一般投訴、一般客服接手或找不到訂單的人工跟進，也可能被誤標為「緊急即日」並再次即時通知。
2. 客人先說「即日訂餐」，再補「8 人」時，分支只把文字加進 handoff 摘要，`wroteInquiry` 仍為 `false`、`quoteId` 仍可為空，沒有先建立或附加 WhatsApp 報價，跟既定「保存後才通知」流程不一致。
3. 客人第一句已包含可落盤資料，例如「今日想訂 30 人到會」，現行 `replyCollect` 完成後會重設為 `identifying`。因此此分支新增的 `awaiting_human` 補充流程反而接不到這類最完整、最常見的即日查詢。
4. 分支會在 `awaiting_human` 階段繼續由 bot 回覆「會即刻通知同事」，與目前 OpenSpec「標記需真人接手後不再自動回覆」的文字契約衝突。若業務希望在同事真正發言前仍自動確認補充資料，必須先把 `queued_for_human` 與 `human_owned` 定義清楚並更新規格。
5. 分支落後 `origin/main` 71 個 commits；targeted tests 雖通過，但 Edge Function typecheck 在舊基線上失敗，不適合整支合併。

建議只移植需求，不移植原判斷方式：

- 對話明確保存 `handoff_kind`（`same_day_catering`／`future_catering`／`order_change`／`general`，其中一般投訴歸入 `general`）、`handoff_urgent`、`handoff_quote_id`；既有 `state` 區分排隊中的 `awaiting_human` 與已接管的 `human_owned`。
- 不再用「有沒有 `selected_order_id`」推斷是否即日或是否屬到會。
- 即日客人補充日期／人數時，先建立或附加報價，再更新同一 handoff，最後才按節流規則通知同事。
- `human_owned` 必須保持完全靜默；`queued_for_human` 是否回一則短確認，按最終業務規則決定。
- 新增回歸測試：完整即日首句後的補充、普通未來到會補充、投訴補充、未找到訂單的改單補充，以及通知節流／失敗時不得聲稱「已即刻通知」。
