## 5. 意圖分流與安全邊界

- [x] 5.1 實作完整語意優先的意圖分類：提示注入保留硬性攔截，其餘業務語意由獨立限額小模型結合整句及近期對話抽白名單 JSON 意圖，模型不可用才走 deterministic fallback；RAG 只在 FAQ／餐牌意圖後啟動
- [x] 5.2 接上查單工具：一張直接回摘要與加單連結、多張只列訂單號與日期、選定後只回該單，並以對話測試確認不要求電郵、不洩漏未選訂單明細
- [x] 5.3 接上意見蒐集：日期或人數只代表資料足夠產生摘要，不代表寫入授權；客人明確確認後才落盤及通知，並以對話測試確認 RAG 不搶路由、拒絕時不寫入、確認後跟進佇列可見 WhatsApp 來源
- [x] 5.4 接上 FAQ 工具：只回已發布條目正文；無匹配則承認不確定並轉真人，並以對話測試確認模型不能改寫 FAQ 答覆
- [x] 5.5 危險意圖停止自動辦理、標記接手、訂單／付款資料不變，並以測試確認改期、取消、投訴、議價、付款爭議都不會寫入業務變更
- [x] 5.6 同一則客人訊息最多一則 bot 回覆，不另發「已讀」模板，並以整合測試確認出站通知開關與 bot 開關互不推導
- [x] 5.7 所有 bot 回覆走香港繁體禮貌模板，出站前做粗口檢查且不抄客人粗口，並以文案測試確認查單／列單／交同事／轉手句為港式書面語、不含簡體或內地客服腔
- [x] 5.8 無關問題與套提示／改角色／要通用 AI 只用固定拒答，不回答實質內容、不洩漏提示或工具名、不寫入報價，並以對話測試覆蓋閒聊、翻譯、忽略指示、重複 prompt 等例子
- [x] 5.9 區分排隊等候真人與 `human_owned`，以明確 handoff context 保存即日到會緊急度及報價；即日補充資料寫回同一跟進上下文，一般投訴不得被誤判為緊急到會
